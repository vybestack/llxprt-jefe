# Issue #451 — Port llxprt-code pr-review delivery process to jefe (Rust)

## Problem

Jefe runs CodeRabbit and OCR as review *signals*, but it has no versioned,
accountable **delivery layer** that turns those signals (plus independent
analysis) into one cross-verified review artifact posted under a known
identity with an explicit verdict and guardrail confirmations. The
`pr-review` process in llxprt-code provides exactly that. This issue brings
that process to jefe, tailored to Rust.

**Corrected understanding (per maintainer):** llxprt-code's `pr-review` is
*not* the Gemini-CLI workflow. It is llxprt-code's own review-delivery
process, complementary to the `ocr` CLI. It combines (a) an OCR CLI pass,
(b) independent source analysis, (c) cross-verification of every finding
against the current source, and (d) a holistic review posted under the
reviewer's own account for traceability, using a CodeRabbit-style structure
(`Overall verdict` -> severity-tiered findings -> guardrail confirmation).

This is the **delivery layer** on top of OCR. It does not replace CodeRabbit
or OCR; it consumes them.

## Decision (accepted approach)

Land **slices P1 and P2** as documentation + a contract test, under TDD:

- **P1** — Add `dev-docs/code-review-process.md` defining the pr-review
  process (OCR pass + independent analysis + cross-verification + verdict +
  tiered findings + guardrail confirmations), with a CodeRabbit-style
  template tailored to Rust (Result/Option, no unwrap/expect, no unsafe,
  deterministic transitions, fail-fast over defense-in-depth).
- **P2** — Embed the Rust guardrail-confirmation checklist in the same
  process doc, mechanically checkable against repo tooling (`cargo fmt`,
  `clippy -D warnings`, no new clippy allows per
  `scripts/check-clippy-allows.sh`, no lint/complexity rule weakening, no
  source/test exclusion, `.llxprt/` untouched).
- **Contract enforcement** — Mirror the `tests/coderabbit_policy.rs` pattern:
  add `tests/pr_review_policy.rs` asserting the defining phrases of the
  process doc and the `CONTRIBUTING.md` link, so CI fails if the process
  silently drifts into a plain OCR dump. This is the maintainer-recommended
  Option B (informed by the issue comment), landed under TDD.

**P3 (the `make pr-review` helper) is NOT in scope** — it is explicitly
approval-gated in the issue. It will be left for a follow-up if the
maintainer approves. The process is fully usable manually.

**Sibling-issue coordination (#449, slice A3):** both #449-A3 and #451-P1
target `dev-docs/code-review-process.md`. This issue owns the
**delivery-format** (verdict + tiered findings + guardrail confirmations +
traceability). #449-A3 owns the **finding-evaluation rubric**
(hypothesis -> verify -> validity -> disposition -> dedupe +
comparison-eligibility). These are two distinct sections of the same doc.
This PR defines the process + delivery format and leaves a clearly-marked
home for the rubric so #449 can add its slice without restructure. The two
issues should not duplicate each other's content.

## Non-goals

- Replacing CodeRabbit or OCR as a review signal. The pr-review process
  *consumes* OCR + independent analysis.
- Auto-posting reviews without human cross-verification. Cross-verification
  against current source is a defining property.
- Implementing P3 (`make pr-review` / helper script) — gated; requires
  maintainer approval. Out of scope for this PR.
- Changing the CodeRabbit demand policy or any lint/complexity rule.
- Changing OCR CI behavior, manifests, or coverage classification
  (those are #449).
- Modifying `.llxprt/`.
- Any Rust production-behavior change. This is docs + a contract test only.
